# 019-cables

## Summary

Cables stay planned and measured in the spreadsheet, which the app imports repeatedly into the Plan as Waypoint, Cable and CableSegment, parsed from the cable ID grammar. Sheet-owned fields are overwritten on every import and app-owned fields are kept. On top of the import, the app tracks segments through ordering, receipt, labelling and packing, and produces cable orders, JJ orders and cable labels. Topology checks compare cable ends and waypoints with Devices, Interfaces and Locations.

## Motivation

- An Episode uses about 1,300 cable rows. The sheet works for planning and measuring, but everything after that is manual:
  - `cables-sum` and `cables-order*` add up orders by medium, colour and length with formulas that break when rows move
  - `jj-order` counts JJs (female-female couplers) by hand from the waypoints
  - `cables-tepra`, `cables-tepra-mmf` are copy-paste label sources, regenerated by hand after each length change
  - receipt checks (納品チェック), preparing and venue confirmation happen on paper or in ad-hoc columns
- Nobody can answer "which cables for `es-tra-01` are still missing?" without reading the sheet row by row.
- Cable ends name devices in shorthand (`trbE`, `xs1`), so a renamed or removed device leaves a cable pointing nowhere and nobody notices until the venue.
- Planning stays in the sheet: it is fast to edit, the team knows it, and measuring happens there. The app takes over from the point where a row becomes a physical thing to order, label, pack and install.

## Explanation

### Vocabulary

| Term | Meaning |
|---|---|
| Cable | One end-to-end run, e.g. `C:as@are/trbE~a`. |
| CableSegment | One physical piece of a run, one row of the sheet's `cables` tab, e.g. `C:as@are/trbE~a A-TRBFO`. The unit that is ordered, labelled and packed. A run without waypoints has one segment. |
| Waypoint | A venue spot where JJs are placed, e.g. `TRBFO`. Optionally inside a Location. |
| 重畳区間 row | A sheet row keyed by a waypoint pair alone (`TRBFO-TRBFI`), holding the length shared by every run between them. Not a segment. |
| CableOrder / line | An order to a vendor, with lines grouped by medium, colour and length. |

### Cable ID grammar

```
<kind>:<a>@<a-location>/<z>[~<member>] [<FROM>-<TO>]
```

- `kind`: `E` External, `B` Backbone, `C` Core, `A` Access.
- `@<a-location>`: the Location slug of the A end (`wlc@noc`).
- End references:
  - `<role><n>`: `tun1` → `tun-01`, `xs1` → `xs-01`
  - bare `<role>`: the only device of that role (`wlc`, `as`)
  - `<location><role letter>[<n>]`: `trbE` → the Edge switch at `trb` (`es-trb-01`); `traE1`, `traE2` → `es-tra-01`, `es-tra-02`
- `~a`, `~b`, …: members of a redundant group (`redundancy_member` 1, 2, …).
- `<FROM>-<TO>`: one piece of a run crossing waypoints; `A` and `Z` are the terminations.

| Row key | Cable | Segment from → to |
|---|---|---|
| `E:ngn1@noc/xs1` | `E:ngn1@noc/xs1` | A → Z (whole run) |
| `C:as@are/trbE~a A-TRBFO` | `C:as@are/trbE~a` | A → TRBFO |
| `C:as@are/trbE~a TRBFO-TRBFI` | `C:as@are/trbE~a` | TRBFO → TRBFI (shared length) |
| `C:as@are/trbE~a TRBFI-Z` | `C:as@are/trbE~a` | TRBFI → Z |
| `TRBFO-TRBFI` | — | 重畳区間 row, supplies the length |

Ends that do not resolve to a Device are kept as text and raise a topology warning.

### Importing

- `CableImportService.ImportCables` takes a branch and the sheet (Google Sheets API read by the backend, or an uploaded XLSX/CSV). TODO(interview): pull through the Sheets API with a service account, or upload? Proposed: Sheets API, with the sheet URL stored on the Episode.
- An import runs as one Mutation and shows a preview first (dry run): created, updated, unchanged, removed, and parse failures per row.
- Matching:
  - Cable by `cable_id`, CableSegment by `row_key`, Waypoint by `code`.
  - Sheet-owned fields are overwritten; app-owned fields (`installed`, segment `status`, `order_line_id`, `labeled`) are kept.
  - A row whose key changed is a new row; the old one is treated as removed.
- Removed rows: TODO(interview): delete, or keep as `removed` so order and label history survive? Proposed: delete segments still `planned`; keep anything further along with a `removed_from_sheet` flag and a warning.
- Waypoints are created from codes seen in segments; their Location and description are app-owned.
- Re-importing an unchanged sheet produces no Changes.

### Segment status

```
planned → ordered → received → prepared → confirmed → installed
```

| Status | Set by |
|---|---|
| `planned` | import |
| `ordered` | attaching the segment to a CableOrderLine |
| `received` | receipt check of the order line (納品チェック) |
| `prepared` | labelled and ready to ship |
| `confirmed` | unpacked and checked at the venue |
| `installed` | laid at the venue |

- `CableSegmentService.MarkStatus` takes many segment ids and a status, so a phone can mark a batch.
- A Cable is `installed` when all its segments are. TODO(interview): derived, or the separate app-owned `Cable.installed` flag in the proto? Proposed: derived; drop the column.
- Moving backwards is allowed (mistakes happen) and recorded in the changelog.

### Orders

- `CableOrderService.CreateOrder` groups selected segments (default: all `planned`) by medium, colour and length into CableOrderLines, and sets them to `ordered`.
- Lengths are the ordered length (`length_m`), not the required one (`required_length_m`, 適正).
- Receipt: enter `received_quantity` per line; segments of a fully received line become `received`. TODO(interview): with a partial receipt, which segments become `received`? Proposed: none until the line is complete; the warning shows the shortfall.
- JJ order: count of JJs derived from segments (one per waypoint crossed per cable), grouped by medium.

### Downloads

All follow the label/download conventions of 015, and can be filtered to a selection (e.g. segments not yet `labeled`, one Location, one order).

| Download | Format | Columns |
|---|---|---|
| Order form (`cables-order`) | XLSX (rasterised in the sheet today) | medium, colour, length, quantity |
| JJ order (`jj-order`) | CSV | medium, quantity |
| Copper label (`cables-tepra`) | CSV | prefix (`E:`), descr (`ngn1@noc/xs1`), length (`2m`), flag (`E:ngn1@noc/xs1\n(2m)`), charlen, type (`2m より線 細径(青)`) |
| Fibre label (`cables-tepra-mmf`) | XLSX (cell line breaks) | flag only, with waypoint pair (`C:cs@noc/fh1E\nSPOFI-SPOFO (2m)`) |

- One label per CableSegment. Downloading labels does not mark them; staff mark `labeled` after printing.
- `charlen` above the tape width's limit raises a warning. TODO(interview): limits per tape width (e.g. 12 mm vs 18 mm)?

### At the venue (phone)

- List segments by Location or Waypoint, with status chips.
- Scan or type a cable label to find its segment. TODO(interview): do cable labels carry a QR code? Proposed: no, search by typed row key prefix.
- Bulk-select and mark `confirmed` or `installed`, offline-capable through 006.

### Warnings (rules under 011)

- cable end does not resolve to a Device, or resolves to several
- A end's Device is not at `@<a-location>`
- resolved Device has no Interface matching a Link to the other end (topology)
- waypoint chain broken: segments of a cable do not form A → … → Z
- `sheet_coupler` differs from the derived JJ count
- shared segment without a matching 重畳区間 row
- label `charlen` too long for its tape
- order line `received_quantity` below `quantity`

## Drawbacks

- Two sources: planners still edit the sheet, and the app is only as current as the last import.
- The cable ID grammar is informal; the parser codifies a convention that may drift between Episodes.
- Matching by key means renaming a cable in the sheet loses its app-owned state.

## Considered Alternatives

- Plan cables in the app: rejected for now. The sheet is quick for bulk editing and measuring, and the team relies on it. Revisit once the import is stable.
- Track cables as Fleet stock in containers: rejected. Cables are consumed per Episode and travel together in the JITBOX in temporary boxes.
- Store label text: rejected; it is derived from the row key and length, so it cannot drift.

## Prior Art

- NetBox cables and cable traces (A/B terminations, path tracing), though NetBox has no notion of waypoints or ordering.
- The current sheet tabs: `cables`, `cables-sum`, `cables-order*`, `jj-order`, `cables-tepra*`.

## Security and Privacy Considerations

- Sheet access uses a credential with read-only scope on the cable sheet. TODO(interview): service account in himari's Google project, or a user OAuth token?
- Import, order and status changes require a Plan-write role (001). Venue status marking may be granted to a narrower venue-staff role.
- Order forms may include vendor contact details; they are not exported to rubykaigi-net.

## Mission Scope

### Out of scope

- Editing cable plans or lengths in the app.
- Cost tracking of orders (stays in a spreadsheet).
- Packing cables into Fleet containers.
- Writing anything back to the sheet.

### Expected Outcomes

- `cables-sum`, `cables-order*`, `jj-order` and `cables-tepra*` tabs are no longer needed.
- Every segment's status is visible per Location, Waypoint and order.
- Topology warnings catch cable ends that no longer match the Plan before the venue.

## Implementation Plan

### Data model

All tables use the `Branched` concern (002): `id uuid`, `branch_id`, `lineage`, `updated_seq`, timestamps; natural keys unique per branch; writes through `Changelog.write`.

```sql
-- db/schema/waypoints.sql
CREATE TABLE waypoints (
  id uuid PRIMARY KEY,
  branch_id uuid NOT NULL,
  lineage uuid NOT NULL,
  updated_seq bigint NOT NULL,
  site_id uuid NOT NULL,
  location_id uuid,
  code text NOT NULL,
  description text,
  created_at timestamp(6) NOT NULL,
  updated_at timestamp(6) NOT NULL
);
CREATE UNIQUE INDEX ASYNC index_waypoints_on_branch_id_and_code ON waypoints (branch_id, code);
CREATE UNIQUE INDEX ASYNC index_waypoints_on_branch_id_and_lineage ON waypoints (branch_id, lineage);

-- db/schema/cables.sql
CREATE TABLE cables (
  id uuid PRIMARY KEY,
  branch_id uuid NOT NULL,
  lineage uuid NOT NULL,
  updated_seq bigint NOT NULL,
  cable_id text NOT NULL,
  kind smallint NOT NULL,
  a_end text NOT NULL,
  location_id uuid,
  z_end text NOT NULL,
  redundancy_member smallint NOT NULL DEFAULT 0,
  comment text,
  a_interface_id uuid,
  z_interface_id uuid,
  a_device_id uuid,
  z_device_id uuid,
  created_at timestamp(6) NOT NULL,
  updated_at timestamp(6) NOT NULL
);
CREATE UNIQUE INDEX ASYNC index_cables_on_branch_id_and_cable_id ON cables (branch_id, cable_id);
CREATE UNIQUE INDEX ASYNC index_cables_on_branch_id_and_lineage ON cables (branch_id, lineage);

-- db/schema/cable_segments.sql
CREATE TABLE cable_segments (
  id uuid PRIMARY KEY,
  branch_id uuid NOT NULL,
  lineage uuid NOT NULL,
  updated_seq bigint NOT NULL,
  cable_id uuid NOT NULL,
  row_key text NOT NULL,
  from_waypoint_id uuid,
  to_waypoint_id uuid,
  shared boolean NOT NULL DEFAULT false,
  required_length_m numeric(6,2),
  length_m numeric(6,2),
  medium smallint NOT NULL,
  color smallint NOT NULL DEFAULT 0,
  sheet_coupler smallint,
  status smallint NOT NULL DEFAULT 1,
  order_line_id uuid,
  labeled boolean NOT NULL DEFAULT false,
  created_at timestamp(6) NOT NULL,
  updated_at timestamp(6) NOT NULL
);
CREATE UNIQUE INDEX ASYNC index_cable_segments_on_branch_id_and_row_key ON cable_segments (branch_id, row_key);
CREATE INDEX ASYNC index_cable_segments_on_branch_id_and_cable_id ON cable_segments (branch_id, cable_id);

-- db/schema/cable_orders.sql, cable_order_lines.sql: same Row columns plus
--   cable_orders: vendor text, ordered_at timestamp, status smallint
--   cable_order_lines: order_id uuid, medium smallint, color smallint, length_m numeric(6,2),
--                      quantity int, received_quantity int NOT NULL DEFAULT 0
```

- `a_device_id` / `z_device_id` are added beyond the tentative proto so an end that resolves to a Device without a specific Interface still links. TODO(interview): keep, or resolve to Interfaces only?
- Enums are smallint, mapped with Rails `enum` to the proto enum values.
- The 重畳区間 row is not stored; its length is copied into each `shared` segment at import. TODO(interview): store shared sections as their own table so a length edit shows up as one Change? Proposed: no, copy.
- Fork (003) copies all cable tables; `order_line_id`, waypoint and interface references are remapped through lineage.

### Code layout

- `app/models/cable.rb`, `cable_segment.rb`, `waypoint.rb`, `cable_order.rb`, `cable_order_line.rb`
- `app/models/cables/id_parser.rb`: `Cables::IdParser.parse(row_key)` → `Data` with `kind`, `a_end`, `a_location`, `z_end`, `member`, `from`, `to`, or a parse error; `shared_section?` for bare waypoint pairs.
- `app/models/cables/end_resolver.rb`: resolves an end reference against a branch's Devices (by role + number, bare role, location + role letter + number). Role letters (`E` → `es`, …) TODO(interview): full table.
- `app/models/importers/cable_sheet.rb`: following 012's importer structure; reads rows, builds a diff, applies in chunks within DSQL limits (3,000 rows per transaction).
- `app/models/cables/jj_counter.rb`: derived JJ counts per cable and per medium.
- `app/models/warnings/cable_*.rb`: rules listed in Explanation, registered with 011.
- `app/models/exports/cable_*.rb`: order form, JJ order, copper and fibre labels (015 conventions).
- Controllers under `app/controllers/api/cable_import/`, `api/cable_segment/`, `api/cable_order/`, `api/waypoint/`.
